# 锁屏消息视频

## 1.51：鱿鱼面板左右自动认（不再需要手动认领）

**1.50 的问题**（设备日志）：左边两块面板的内容签名其实是 `icons8|pc1|dots38`（180pt 高）和 `icons4|pc1|dots38`（95pt 高）——分页条都在、圆点宽度一样，只有图标数和高度不同；于是「按形状找空槽位 + 图标数最近邻」把两块都判给了同一个槽位（日志里两块都 `slot=3`），用户只能手动认领，还容易认乱。

**1.51 的改法**：判定顺序里加了一条「**同一侧的两块面板自己排序**」——上滑是那一对里**更高**的那块（高度差 ≤4pt 时看图标数，上滑的图标数更多），因为设备数据里两边都成立：

| 侧 | 上滑 | 上上滑 |
|---|---|---|
| 右 | icons50 / 435pt | icons29 / 350pt |
| 左 | icons8 / **180pt** | icons4 / **95pt** |

| 规则 | 说明 |
|---|---|
| 见过的签名 | 直接归位（老规矩，改面板也不丢），并**顺手检查这一对有没有排反**，排反了就地对调 |
| 没见过 + 一侧学过 | 判给**还没学过的那一侧**（右边先配好，所以新面板=左边；反之亦然） |
| 该侧只认得一块 | **成对排序**：新面板比已记的那块高→它是上滑；矮→它是上上滑；已记的那块随之挪到对侧 |
| 两侧都认得 | 当"面板被改过"，按图标数最近的槽位归属，**不动**别的 |
| 该侧一块都没认 | 分页条 → 绝对高度 → 默认上滑（下次打开就会被排序纠正） |

所以：**不用点认领了**——左边两块面板各开一次，它们会自己排好（高的走「左边上滑素材」，矮的走「左边上上滑素材」）；1.50 那种认反/认重的状态，下次打开就自动对调回来。「认领刚用过的面板」这一行保留着，当最后手段。

诊断行也加了两处，下一份日志能把判决看全：

```
squid-panel win=SGPanelWindow 430x932 slot=2 gesture=左边上滑 play=左边上滑 \
  why=pair-by-height-left@slot2 sig=icons8|pc1|dots38 pair=180/95 mode=content …
```

## 1.50：鱿鱼面板四套素材（右边/左边 × 上滑/上上滑）+ 认领入口 + 修双「播放声音」

| 改动 | 说明 |
|---|---|
| 素材从 2 套变 **4 套** | 设置页与悬浮窗都改成：`切换右边上滑素材` / `切换右边上上滑素材` / `切换左边上滑素材` / `切换左边上上滑素材`，密钥 `SquidPanelVideo` / `SquidPanel2Video` / `SquidPanel3Video` / `SquidPanel4Video` |
| 槽位表 | 内核从「两个形状记两条签名」改成「**四个槽位各记一条签名**」（`SquidPanelSlot1Sig`…`SquidPanelSlot4Sig`），1.48 的 `SquidPanelTallSig2`/`SquidPanelShortSig2` 自动作为右边两个槽位的初值，老设备的右边学习结果不丢 |
| 形状判据 → 形状 + 归属 | 形状（上滑=高版 / 上上滑=矮版）仍按分页条与高度判定；**左右无法从内容里看出来**（两边面板只差你自己放进去的东西），所以没见过的面板先「认领」它那个形状里还空着的槽位（先右后左） |
| **认领刚用过的面板** | 一侧的形状判错了、或左右认反了，用手势调出那个面板→关掉→点这一行选它属于哪一套素材；内核把刚才看到的面板重绑到你选的槽位（同时解掉旧的绑定），日志出一行 `squid-panel-claim` |
| 对调 | 「对调上滑 / 上上滑素材」改成**同侧内**对调（0↔1、2↔3），不会再把左右两套素材搅在一起 |
| 修双「播放声音」 | 悬浮窗鱿鱼分区从 6 行加到 9 行（4 素材 + 认领 + 对调 + 声音 + 音量），音量行原来落在规则外，被渲染成第二个「播放声音」开关；现在第 8 行是真正的音量滑块 |
| 诊断行 | `squid-panel win=… slot=1..4 gesture=右边上滑 play=… why=… sig=…` —— 一眼看出这个面板被判给了哪套、走的哪条判据 |

声音与音量仍是四个面板**共用**（同时只可能有一个在屏幕上）。

## 1.49：CopyVault 面板背景视频改为「认名字」，横竖屏统一

**日志给的结论**（两次设备日志，竖屏 + 横屏）：

| 场景 | 1.48 挑中的"卡片" | 结果 |
|---|---|---|
| 竖屏正常 | `CopyVaultView@5,497,420,430` vis=180600 | ✅ |
| 竖屏：上面出现更高的面板 | `UIDropShadowView@0,434,430,498` vis=214283 | ❌ 视频铺满整屏 / 跑上面面板上 |
| 横屏正常 | 同样被 916×722 的 `_UIRoundedRectShadowView`（vis=393880）抢走 | ❌ 挂到错的面板上 |

**原因**：1.43–1.48 的卡片判据是「同一窗口里**可见面积最大**的那个视图」。剪贴板面板自己会往同一个 `CVPanelWindow` 里推一个**更高的**面板（预览/工具条 sheet），面积一大就把剪贴板顶掉，视频跟着跑；横屏同理，被 916×722 的阴影视图抢走。**竖屏横屏是同一个毛病**。

**改法（`LMVCopyVaultPanelVideo.h`）**：

| 改动 | 说明 |
|---|---|
| 卡片**认名字** | 只认 `CopyVaultView`（排除 TableView/Cell/Scroll 这些内容行），别的更高的面板一律无视 —— 只认身份，不认大小 |
| 三态区分 | 「插件不在树上/被改名」→ 回退到面积判据；「找到了但停在 y=1454（面板关着）」→ 直接卸载不上视频 |
| 材质夹在卡片内 | 毛玻璃必须 ≥90% 落在卡片范围内，全屏背景再也抓不到，视频不会溢到面板外 |
| 诊断行加 `why=` | `why=vault` / `why=generic`，下一份日志一眼能看出走的哪条路 |

## 1.48：修 1.47 的两个错 ——「只学过一个面板时，另一个就是另外一个」＋ 不再互相覆盖签名

**1.47 的日志给了结论性的数据**（这三行签名是设备上的真值）：

| 面板 | 签名 | 1.47 的判定 |
|---|---|---|
| 上滑 | `icons50\|pc1\|dots55` | tall ✅ |
| 上上滑（**加高前**） | `icons19\|pc1\|dots38` | short ✅ |
| 上上滑（**加高后**） | `icons29\|pc1\|dots55` | ❌ 判成 tall |

**三个签名完全不同，本来就能分开** —— 说明"图标数"这条判据是对的。问题出在我 1.47 的两处：

1. **新签名还是先跑外观判据**：`icons29` 第一次出现时，走的仍是"分页条可见 → tall"，于是判成 tall（加高后分页条也出现了，这条判据必然失效）。
2. **新签名会覆盖旧记录**：于是 `icons29` 把 `icons50` 的记录顶掉，下次打开上滑又变"首次"，两个签名互相挤、来回重学（日志里 `146003` 那行 `icons50` 又变成 `page.hidden=0` 就是这个）。

**改法（`LMVSquidPanelVideo.h`）**，判定顺序重排：

| 顺序 | 条件 | 结论 |
|---|---|---|
| (a) | 签名与记住的某个**完全相同** | 直接用（`why=sig-tall` / `sig-short`） |
| (b) | **只学过一个形状**，而这个签名不是它 | **它就是另一个面板**（排除法）→ `why=other-panel` |
| (c) | 两个都学过、且都不匹配 | 按**图标数最近邻**归属 → `why=nearest-short` / `nearest-tall` |
| (d) | 一个都没学过（或打平） | 才用内容判据（分页条 → 高度），并记下来 |

(b) 就是为你这个场景加的：**先把上滑学成 tall，之后任何"没见过又不是它"的签名必然是上上滑** —— 你把它加多高都不影响。

另外两点：

- **签名记录的键改名**（`…Sig` → `…Sig2`）：1.47 在设备上已经存了一条**错的结论**（`icons29` 记成 tall），换一代键名让它**自动作废**，从零学一次，而不是把错的迁移过来。
- **不再记录"没加载完"的签名**（图标数为 0 时不记），避免面板还在组装时记下垃圾。

> 建议升级后按这个顺序各呼出一次：**先上滑面板**（学成 tall），**再上上滑面板**（自动判为 short）。这样一次到位；万一顺序反了导致两边都对调了，设置里的「对调上滑 / 上上滑素材」一次就能翻正。

## 1.47：改用「内容签名」分辨两个面板（1.46 的按对象记没起作用）

**1.46 为什么没修好。** 1.46 记的是**卡片对象**。设备日志（1.46 跑出来的）把这条路堵死了：34 秒里出现了 **4 个不同的 tall 卡片指针**（`0x80e5956d0` / `0x80e574970` / `0x80ef99fe0` / `0x80e18a210`）——

> **每次呼出面板，卡片都是全新对象。** 所以"记住对象"只在单次打开期间有效，一关一开就忘，又退回去看外观。

**1.47 改用「内容签名」。** 签名里**不含高度、也不含宽度**，只有：

| 分量 | 说明 |
|---|---|
| `icons` | 卡片里 `UIButton` 的总数（图标个数） |
| `pc` | 这张卡片自己的分页条是否存在 |
| `dots` | 分页条内容宽度（反映页数，竖屏高版 55、低版 38） |

这些在**横竖屏一致**，而且**你把面板加高不会变**。签名按形状分别记住（存进 prefs，跨重启有效）。

判定顺序：

1. **签名精确命中** → 直接用记住的形状（`why=sig-tall` / `sig-short`）；
2. **签名没见过，但只有一个已记住的签名与它“图标个数相同”** → 认定是同一个面板（只是变高/变宽了），沿用它的形状并更新签名（`why=icons-tall` / `icons-short`）——**"我把上上滑改成和上滑一样高"就落在这一条，材质保持不变**；
3. 完全陌生 → 才用内容判据（分页条 → 高度兜底），并把这个签名的结论记下来（`why=page.hidden=…` / `height=…`）。

**诊断又加了一列** `sig=`：`squid-panel … shape=… slot=… why=… sig=icons15|pc1|dots55 …`，`why=` 一眼能看出这次是"签名命中"还是"重新学的"。

**前提（要跟你说清）**：签名靠"图标个数 + 页数"区分。所以**两个面板的图标数量（或页数）不能完全一样** —— 真配成完全一样，就没有任何信息能分辨了，只能两个用同一个素材。1.46 的「对调上滑 / 上上滑」开关保留，用于万一首次学反了。

## 1.46：两个面板改用「对象身份」分辨（你把面板改高也不会再认错）

**问题**：把上上滑面板**加高**之后，它开始用上滑那条素材了。

**根因**：1.44/1.45 分辨两个面板用的是**面板长什么样**（分页条可不可见，其次是高度占屏比例）。这两个判据都跟着**内容**走 —— 你把面板加高，它就长得更像上滑面板，于是被判成"上滑"，去用槽①。

> 设备日志给的四个样本本来还分得开（竖屏 435/350、横屏 340/180；分页条 h0/h1），但那是**在你改面板之前**。

**改法（`LMVSquidPanelVideo.h`）**：改成按**对象身份**分辨。

- 这两个面板是**两个独立、长期存在的对象**。某张卡片**第一次**被分类时，插件就**记住这个对象**是"上滑"还是"上上滑"（`__weak` 引用，对象销毁自动失效）。
- 之后**只要还是这个对象**，就直接用记忆里的结果 —— **内容判据（分页条/高度）只在第一次见到时跑一次**。所以你再怎么改面板（加图标、加高、多出一个分页条）都**不会再翻转**。
- 万一**首次判断就猜反了**（或者面板对象被重建后重新猜错），设置里有 **「对调上滑 / 上上滑素材」**：一键把两个形状用的素材对调（设置页是开关，悬浮面板里是那行按钮，点一次切一次，行尾显示"正常 / 已对调"）。

**诊断也补齐了**，`squid-panel` 那行现在会说清一切：

```
squid-panel win=SGPanelWindow 430x932 shape=short slot=2 why=remembered mode=content card=SFActivityPanelView@0,582,430,350 ptr=0x… vis=… live=… host=430x350
```

| 字段 | 含义 |
|---|---|
| `shape=` | 这次判成哪个形状 |
| `slot=` | 实际用了哪个素材槽（1 / 2） |
| `why=` | 判定依据：`remembered`＝记忆命中（最理想）；`page.hidden=…/gap=…`＝靠分页条；`height=…`＝兜底判据 |
| `ptr=` | 卡片对象地址 —— 下次若怀疑"对象被重建了"，看这个地址变没变就知道 |

README 里 1.45 那条"槽空就不挂"的行为**不变**：两个槽依旧各自独立。

## 1.45：两个素材槽改成完全独立（低版没设素材就不再借用上滑那条）

1.44 里两套素材是"带回退"的：低版（上上滑）没设素材时会借用上滑那条。按要求改成**完全独立**：

- **上滑面板** → 只用「切换上滑素材」（`SquidPanelVideo`）
- **上上滑面板** → 只用「切换上上滑素材」（`SquidPanel2Video`）
- **某一槽为空** → 那个面板**什么都不挂**：保持原样，视频层不插入、也不出声（detach 同时把共用的声音通道按下去）

声音开关与音量仍是两套共用（同一时刻只有一个面板在屏上），选槽只看卡片的分页条，与横竖屏无关。

顺带加了一条诊断：槽为空时打印

```
squid-panel shape=tall|short slot=empty (no video, by design)
```

这样日志里能一眼分清"这个面板本来就没配素材"和"通道坏了"（后者会打出正常的 `mode=/card=/host=` 一行或什么都不打）。

> 提醒：素材选择器目前没有"清空选择"入口 —— 某个槽一旦选过素材，想回到"空"需要把那个素材删掉（删除素材会自动取消相关选择）。

## 1.44：鱿鱼面板的两套素材（上滑 / 上上滑）＋ 低版横屏的视频挂载修正

**这个面板其实有两套。** 1.42 加深出来的 `desktop-panel-tree` 把两套都拍全了：

| | 上滑（高） | 上上滑（低） |
|---|---|---|
| 竖屏卡片 | 430×**435**，底边 932 | 430×**350**，底边 932 |
| 横屏卡片 | 814×**340**，底边 430 | 814×**180**，底边 430 |
| 分页条 `UIPageControl` | **可见（h0）**，指示点区 27pt | **隐藏（h1）**，指示点区 10pt |
| 内容滚动区 | 竖屏 425 / 横屏 330 | 竖屏 340 / 横屏 170 |

两套各自还有"屏内 + 屏外停放"两个副本（竖屏停在 y=1459 / 1544，横屏停在 y=710 / 550），而且**底边对齐**（停靠底边竖屏 1894、横屏 890）。

**怎么分辨两套**：尺寸只是表象 —— 横屏低版占屏高 41.9%，竖屏高版占 46.7%，按比例定阈值会翻车。可靠的是**分页条**：它只属于其中一个面板，在四个副本里都贴在**各自卡片正上方 20pt**，并且高版可见、低版隐藏，横竖屏完全一致。代码取"底边贴着卡片顶边的那个分页条"，取不到才回退到屏高 45% 的尺寸判据。

**两个毛病一起修**

1. **低版横屏"挂载太低"**：材质是**整屏尺寸**（932×435），而卡片只有 814×180 —— 拿卡片那条"自身至少一半可见"的规则去算材质，比例只剩 36%，材质被当成"停在屏幕外的副本"排除，视频于是退化成贴在卡片的**第一个子视图**上，**压在毛玻璃下面看不见**。现在材质的判据改成「**是否覆盖卡片**」（窗口坐标里盖住卡片 ≥90% 即认）；卡片自己的"一半可见"规则**保持不变**，屏外副本照旧被挡。
2. **视频比面板大**：原来 host 的尺寸取的是**容器**的尺寸（contentView / 材质），横屏下容器是 932×435、卡片只有 814×340，视频就溢出了面板。现在统一取**容器与卡片的交集** —— 两种形态、两个方向都正好铺满面板本身。

**新增第二套素材**：设置页与小彩蛋悬浮面板各多一行 —— 「切换上滑素材」（`SquidPanelVideo`）/「切换上上滑素材」（`SquidPanel2Video`）。运行时按当前卡片的分页条判形态选素材；**某个槽留空则回退到另一槽**，老用户升级不会突然没有背景。声音开关与音量**两套共用**（同一时刻只有一个面板在屏上）。素材删除路由、素材库允许目标、悬浮面板的音频行号（3/4）全部同步。

## 1.43：CopyVault（剪贴板面板）背景视频通道

**形状来自 1.42 加的诊断**（`desktop-panel-tree` / `desktop-window-meta`），和鱿鱼面板是同一路：

```
CVPanelWindow@0,0,430,932 lvl=10000010 rvc=CVPanelViewController
  UIView@0,0,430,932 → CVPanelView@0,0,430,932 → UIControl@0,0,430,932
    CopyVaultView@5,497,420,430          ← 卡片（关着时停在 @5,1454，屏幕外）
      UIVisualEffectView@0,0,420,430 r55  ← 毛玻璃材质（与内容容器是兄弟）
      UIView@0,0,420,430 r55              ← 内容容器（表头 + 三张表）
```

**判定规则（照鱿鱼那套，但有两处按设备事实单独处理）**

- **窗口**：类名含 `CVPanel`（兜底 `CopyVault`）——CopyVault 有**自己的窗口**，所以通道只认这个窗口，不会像 AT 早期那样认错卡片。
- **卡片**：窗口内**最大且非全屏**、**至少一半在屏内**的可见后代 → `CopyVaultView`。关着时它停在 `y=1454`（屏幕外），"一半在屏内"这条规则就是用来排除那张停在外面的副本的。
- **挂载**：插进材质的 `contentView`（在模糊之上）；因为**内容容器是材质的兄弟**，所以同时还在内容之下 —— 就是 1.24 给鱿鱼定的"图标下方、材质上方"那一层。
- **圆角**：卡片本身是 **r0**，圆角在材质/内容容器上（**r55**）——所以圆角取值来自材质而不是卡片，否则视频层会是直角压在圆角卡上。

**接入点（全部照 AT / 鱿鱼现成套路）**：开关 `CVBackgroundEnabled`、素材 `CVVideo`、声音 `CVSoundEnabled`、音量 `CVVolume`；设置页与悬浮面板各一处入口，**都排在 AT 视频背景正下方**；素材库/删除路由、音频通道列表（第 11 条 `CV`）、安装钩子/刷新/挂起全部同步。

## 1.42：小彩蛋悬浮窗的内容位置与面板位置彻底解耦（1.41 没修干净）

**两个方向都出现过，第二个才是 1.41 遗留的**：

| 现象 | 面板顶 → 第一行白卡片（截图实测） | 缺/多 |
|---|---|---|
| 拖到最上面时"消息背景文字跑到下面" | 123pt | 多了一份状态栏高度 |
| 换个位置时"消息背景太高、压在标题栏上" | **27.7pt** | 少了导航栏那 44pt |

正常值是 **44（导航栏）+ 26（分组头）= 70pt**。

**根因（两个）**

1. 面板是 `UITableViewController`，表格默认 `contentInsetAdjustmentBehavior = .automatic`，会按**表格自己的安全区**自动加内边距 —— 面板顶被拖到窗口安全区分界线时，除导航栏 44pt 外又叠加一份状态栏高度 → 内容整体下移。
2. 1.41 改成 `.never` + 常量内边距，方向是对的，但**只从 `viewDidLayoutSubviews` 里下发** —— 这个面板是手动 `addSubview` + 手动设 frame 的浮动卡片，它的布局不保证在用户看到之前跑过，于是那次内边距可能**根本没下发**（表格内边距仍是 0）；而 `.never` 的滚动视图**又不会自己 seek 到 `-contentInset`**，两个原因叠起来，内容就顶到了状态栏下沿 → 「消息背景 太高」。

**改法（`LMVEasterPanel.h`）**

- `viewDidLoad`：`contentInsetAdjustmentBehavior = .never`，并**立刻**调用 `[self pinBarInset:YES]` —— 内边距在面板显示之前就已生效，不再依赖布局时机。
- `pinBarInset:` 把 `contentInset.top` 钉在导航栏高度（取不到时回落 44pt），并在 `seekTop` 时**显式把落位滚动位置设成 `-bar`**，补上 `.never` 不自动 seek 的那一步。
- `viewDidLayoutSubviews` 只做同步（`seekTop:NO`），永不碰用户的滚动位置。

结果：面板在任意位置，内容都从导航栏正下方开始（70pt），且**不会**因为面板移动而变。

**诊断同步加深（为了下一步挖剪贴板面板）**

- 新增 **`desktop-window-meta`**：每个窗口打 `类名@x,y,w,h lvl=窗口层级 hid=是否隐藏 a=alpha rvc=根视图控制器类名`，**包含隐藏窗口** —— 用来判断某个面板是不是"开了才出现的窗口"、以及哪个窗口属于哪个插件。CopyVault 的 `CVPanelWindow` 常驻但空着，只有这一行能说明问题。
- 新增 **`desktop-panel-tree`**：对所有**类名含 `Panel` / `Menu` / `Platter` / `Clipboard`** 的窗口打**六层**完整子树（每节点带 frame/hidden/alpha/圆角），并且**不跳过隐藏窗口**。原来的 `desktop-panel` 只到三层、每层 6 个、且来源窗口表会跳过隐藏窗口，所以 `CVPanelWindow` 一直只显示成 `{UIView[]}` 空壳。

顺带把诊断版本号对齐到 1.42。

## 1.41：小彩蛋悬浮窗移到最上面时，内容不再整体往下掉

**现象。** 把悬浮窗（`背景视频` 面板）拖到最上面时，标题栏下面多出一大块空白，`消息背景` 以及它后面的每一行都整体下移；把面板往下拖就恢复正常。

**根因。** 面板是 `UITableViewController`，滚动视图默认 `contentInsetAdjustmentBehavior = .automatic`：它会按**滚动视图自己的安全区**自动加内边距。当面板顶部被拖到窗口安全区分界线（刘海/状态栏下沿）时，表格除了导航栏那 44pt，**又叠加了一份状态栏高度的顶部内边距**，内容因此整体下移。面板在下方时这份额外内边距为 0，所以只有「拖到最上面」才出现。

**截图实测**（两张截图同为 1024×2219，2.381 px/pt）：面板顶 → 第一行白卡片，靠上时 **123pt**，靠下时 **70pt**；70 = 导航栏 44 + 分组头 26，正是正常值，多出来的约 53pt 就是那份状态栏内边距。

**改法（`LMVEasterPanel.h`）。**

- `viewDidLoad`：`self.tableView.contentInsetAdjustmentBehavior = UIScrollViewContentInsetAdjustmentNever;` —— 表格不再按安全区自动加内边距。
- 新增 `viewDidLayoutSubviews`：把 `contentInset.top` 钉在导航栏高度（浮动面板恒为 44pt，取不到时回落 44）。

这样面板在任意位置，内容都从导航栏正下方开始；面板在下方时的观感与改动前**完全一致**。

顺带把诊断版本号对齐到 1.41。

## 1.40：主屏长按菜单不再串出 AT 面板背景视频的声音

**现象。** 开启视频声音后，先呼出 AT 面板背景视频，再回桌面长按 App 图标弹出菜单 —— 菜单背景视频出现的同时，**AT 面板背景视频的声音还在响**。

**根因。** AT 通道的探测口径太宽。AppTools 没有自己的窗口，它把面板 present 进 `SBHomeScreenWindow`、在 `TransitionView` 下一两层，所以 1.28 的探测是「从 `SBHomeScreenWindow` 出发，认**任何类名带 `TransitionView` 的子树**，取最大可见非全屏卡片」。而**系统长按菜单**用的过渡容器叫 `_UIContextMenuPlatterTransitionView`，**名字里同样有 `TransitionView`**；主屏图标那条菜单又**同样建在 `SBHomeScreenWindow`**。于是 AT 通道把**菜单的卡片当成了 AT 面板**：视频挂上去，音轨可见性随之成立，声音就和菜单一起响了。

对照很清楚：鱿鱼面板通道不会串，因为它锁的是**独立窗口**（类名含 `SGPanel`）；AT 通道锁的是**共享的 home 窗口**，所以必须自己把系统菜单排除掉。

**改法（`LMVATPanelVideo.h`）。**

- `LMVATPanelSystemMenu(view)`：类名含 `ContextMenu` 即判定为系统菜单（`_UIContextMenuPlatterTransitionView` / `_UIContextMenuContainerView` / `_UIContextMenuView` / `_UIContextMenuListView` 全部命中）。
- `LMVATPanelTransitionRoots`：遇到系统菜单节点**直接 return**，不再把它或它的任何后代当作 AT 的过渡容器。
- `LMVATPanelCard`：候选卡片命中 `LMVATPanelSystemMenu` 一律跳过。

这样菜单出现时 `LMVATPanelCard` 返回 nil → AT 通道 `detach` → `setVisible:NO` → 音轨在 AT 自身的 0.1s 轮询 / 音频 0.25s 同步内暂停。AppTools 自己的面板是普通 `UITransitionView`、类名不含 `ContextMenu`，挂载不受影响。

顺带把诊断头里的版本号对齐到 1.40（`Tweak.xm` 里那行此前硬编码 `version=1.31`，`LMVThumbnailDiagnosticLog.h` 里是 `version=1.25`）。

## 1.39：回到 1.30 的挂载位置（视频进安全窗口），dock 消失的根因从窗口层面消除

1.38 的私有 backdrop 分组名方案（LMVDesktopIsolateFromBackdrop）用户实测**无效** —— dock 仍消失。
于是退回 1.30 实锤有效的口径：**视频挂回 `_SBWallpaperSecureWindow`（经壁纸承租 lease）**。

根因是窗口层面的：dock 的浮动毛玻璃**只采集它自己所在的窗口**（per-window backdrop capture）。
- 1.31+ 把视频搬进主屏窗口后，dock 的 backdrop 就把这块全屏视频算进去了 → dock 外观随视频变化 → 表现为「长按菜单时 dock 消失」。
- 1.30 视频在安全窗口（另一个窗口），dock 的 backdrop 采不到它 → dock 正常。

主屏窗口本来就是透明的、透出安全窗口这一层，所以视频照旧铺满桌面，**无需任何额外的视图遮蔽**
（1.38 那种"隐藏主屏壁纸层"的做法既多余，还可能误伤 dock 自身背景，已整体删除）。

| 项 | 1.39 |
|---|---|
| 桌面视频尺寸 | 满容器（1.32 口径） |
| 1.33~1.37 的 dock 让位机制 | 已删除 |
| 1.38 的 backdrop 分组方案 | 实测无效，已删除 |
| 视频挂载位置 | 回到 1.30 安全窗口（lease 路径） |
| 主屏壁纸遮蔽 | 不需要，已删除 |
| 逐帧监视器兜底间隔 | 已回到 1 秒（1.38 收紧到 0.25s 是为让位服务的，让位没了） |
| 1.34 的素材预览图冷启动预热 + 全量请求 | **保留**，未改动 |

**取舍说明**：与 1.32 相比，这一版退回了"桌面 App 长按菜单背景显示视频"那一项（因为视频不在主屏窗口，
菜单的 backdrop 同样采不到它）。换来的是 dock 在任何长按菜单下都稳定存在 —— 这正是你确认 1.30「没问题」的状态。
若你确实想让菜单背景也有视频、同时 dock 不消失，那是 window-local backdrop 与 dock-menu 共享主屏窗口的固有矛盾，
需要换一条更激进的路（例如给菜单背景单独喂图而非依赖 backdrop 采样），可另行评估。

## 1.38：回到 1.32 的尺寸口径，把 dock 的问题处理在源头

按要求，桌面视频尺寸重新固定为**满容器**（1.32 的行为），1.33~1.37 长出来的整套
「让出 dock 条带」机制连同它的菜单探测链**全部删除**。让位从来只是绕过症状：它确实
让 dock 恢复，代价是那一条永远没有视频。

**问题的真正分界线**（日志给得很干净）：

| 版本 | 视频挂在哪 | dock |
|---|---|---|
| 1.30 | `_SBWallpaperSecureWindow` | 正常 —— **安全窗口的内容不参与系统毛玻璃的背面采集** |
| 1.31+ | `SBHomeScreenWindow` | 异常 —— 普通窗口的内容参与，dock 的 `SBFloatingDockView` 开始采样整块全屏视频 |

**改法**：`LMVDesktopIsolateFromBackdrop()` —— 给视频层一个独立的 backdrop 分组名
（`_setBackdropGroupName:` / `_setGroupName:` / `setBackdropGroupName:` 依次尝试，全部带
`respondsToSelector` 守卫）。系统的毛玻璃不带这个分组名，按该机制就不应再把这一层算进去，

另外把逐帧监视器的兜底探测间隔改回 **1 秒**（0.25 秒是为了让位跟上菜单动画才收紧的，

## 1.37：修 1.36 仍然收走 dock 视频的错（过渡容器被当成了菜单）

1.36 用的是**层序遍历**，而窗口里第一个节点就是
\`_UIContextMenuPlatterTransitionView\` —— 它是**覆盖整个屏幕**的过渡容器

照旧让位。用日志里的真实层级重放两种算法：

| | 取到的对象 | frame | 底边 | 条带顶边 | 结论 |
|---|---|---|---|---|---|
| 1.36 旧算法 | \`_UIContextMenuPlatterTransitionView\` | 0,0,430,932 | 932 | 838.3 | 让位（视频被收走） |
| 1.37 新算法 | \`_UIContextMenuView\` | 147,389,250,447 | **836** | 838.3 | 不让位（视频铺满） |

也省掉扫 dock 那堆图标。断言同步：platter 若被当作返回对象，本地测试直接报错。

## 1.36：dock 让位只在菜单真的压到它时才发生（修 1.35 的误判与抖动）

1.35 只要屏幕上「存在菜单」就让开 dock 条带，结果两个毛病：

- **误判**：探测从第一个窗口开始、用 80 个节点的共享预算，走到哪个窗口全凭当时树的大小。
  日志里同一个长按期间让位/恢复反复了四次（110944.347 让、110946.351 恢复、110949.150 又让），
  而当时屏幕上唯一的浮层只是**图标被提起的 platter**（`SBIconDragPlatterWindow`），根本没有菜单。
- **无权让位**：日志把菜单的真实位置钉死了 ——
  `SBFloatingDockWindow{_UIContextMenuPlatterTransitionView{_UIContextMenuView@147,389,250,447}}`，
  底部 = **y 836**，而 dock 条带从 **838.3** 开始。菜单**根本没碰到 dock**，却把那一条的视频收走了。

现在：探测只搜**菜单真正会被建在两个窗口**（`SBFloatingDockWindow` / `SBHomeScreenWindow`），

## 1.35：dock 那一整条恢复显示视频（让位改为只在长按菜单出现时）

1.33 为了让悬浮 dock 不被长按菜单遮出问题，把桌面视频的高度**永久**减掉了 dock 条带 ——
结果那条区域永远只显示系统背景，就是你看到的「dock 下面没有视频背景」。现在让位改为
**跟着菜单走**：平时视频铺满整屏，只有主屏长按菜单（包括长按 dock 上的图标）弹出来时
才让开。

- `LMVDesktopContextMenuUp()`：探测系统自己的菜单类（`_UIContextMenuListView` /
  `_UIContextMenuView` / `_UIContextMenuPlatterTransitionView`），把两条菜单路径统一到
  同一个判据上 —— 悬浮 dock 走的是 platter 那条，**不经过**
  `_UIContextMenuPresentationController`。判据放在 dock 子树遍历**之前**，所以平时连那次
  遍历都省掉了。三个类名都认不出来时**保守让位**（等于保持 1.33 的行为），不让 dock 冒险。
- 让位的**触发**交给桌面通道自己的逐帧监视器：它原先在「可见窗口数没变」时的兜底间隔是
  1 秒，而菜单是在**已经存在的窗口内部**弹出的浮层、不改变窗口数，1 秒的兜底会让让位明显
  滞后于菜单动画。间隔收紧到 **0.25 秒**，让位就与菜单那约 0.3 秒的弹出动画同步。这仍然
  是每秒 4 次探测，比它当初取代的逐帧探测低两个数量级。

菜单弹出期间 dock 条带仍然让开（1.33 修好的那件事不变），菜单消失后立即恢复铺满。

## 1.34：注销后打开素材列表不再满屏「生成中…」（冷启动预热 + 全量请求）

**日志给出的结论：机制没有问题，只是「冷启动没人提前去拿图」。** 一次 9 个素材的打开记录：

- `picker-appear` → `catalog-ready`：**28 ms**
- 第 1~5 行出图：**68 ms**（图片出现前会先插一个占位状态）
- 第 6~9 行出图：**0.65~0.93 秒**——它们只有等到 UITableView 预取才会被请求，所以往下滑就会看到「生成中」
- 10 秒后第二次打开：**全部 `memory-hit`，一张占位都没有**
- 全程 **`disk-hit`，解码 0.7~9.0 ms**——磁盘缓存一次都没漏

**为什么偏偏是「注销后」**：注销会重启 SpringBoard，**内存里那张缩略图缓存跟着清空**，而磁盘上的 sidecar 记录其实完好。所以每次注销后的第一次打开，9 行都得重新走一遍「读磁盘 → 贴图」，这个过程虽然不足 1 秒，但肉眼能看到占位状态。

**改动（只改「什么时候去拿图」，不改任何判断逻辑）**：

- **`+[LMVMaterialPicker prewarmThumbnailCache]`**：在启动就绪时派一个后台任务，把磁盘上已有的缩略图**批量读进内存缓存**。这样注销后第一次打开直接走 `memory-hit`，和第二次打开完全一样。后台队列、不建 UI、不建播放器，**只读已存在的 sidecar，从不解码**；没有 sidecar 的行留给正常路径。
- **`-requestAllThumbnails`**：目录读完后请求**所有行**，不再只请求可见行。磁盘命中时每行约 1 ms，9 行共约 9 ms；只有缓存未命中才真的解码。
- **worker 并发 2 → 4**：磁盘命中时成本可忽略，只在首次解码那一波起作用；峰值仍由 `-requestThumbnail:` 里的 pending 上限约束。
- 共享缩略图状态从 `-init` 内部提到**文件作用域**（`LMVMaterialSharedState()`），因为预热必须能在任何 picker 实例存在之前就准备好缓存。变量名保持不变，原有的共享契约描述仍然成立。

## 1.33：修复长按菜单时底部悬浮 dock 看不见（桌面视频层不再压到 dock 条带）

**现象与定位。** 1.30 正常、1.31 起异常：长按主屏图标弹出菜单时，底部悬浮 dock 看不见。日志给出的证据很干净——**`SBFloatingDockWindow` 的内容在菜单前/中/后三次 dump 完全一致**，窗口 alpha 1.00、图标容器和背景材质都在。所以不是"dock 被我们改了"，而是 **dock 的视觉合成**被改变了。

**机制。** 1.31 把视频从 `_SBWallpaperSecureWindow` 搬进了 `SBHomeScreenWindow`（那是修「开始桌面视频 不在桌面」的改动）。关键区别：**secure 窗口的内容不参与系统 backdrop 采集，普通窗口的内容参与**。于是 dock 的悬浮毛玻璃（`SBFloatingDockView`）开始采样我们**整块全屏**的视频，dock 自己的外观就跟着变了。1.30 之所以正常，是因为当时视频在 secure 窗口里，dock 根本采不到它。

**改法。** 不给 dock 采——**Home 宿主路径下，视频高度收缩到 dock 条带之上**：

- `LMVDesktopDockInset()`：从 `SBFloatingDockWindow` 里实测 `SBFloatingDockView` 的 frame 得到 dock 高度（**实测而非写死**：dock 会随 Reachability、旋转、机型移动和改变大小），并带合理性上限（超过屏幕 40% 视为异常，归零）。
- `LMVDesktopVideoBoundsFor()`：唯一的尺寸口径。Home 宿主路径减去 dock 条带；**其他所有路径（壁纸宿主等）保持原来的满容器尺寸，行为不变**。
- `-update` 与 `-syncGeometry` 都改用这个口径，所以一次普通布局也不可能把视频悄悄长回 dock 上面去。
- `homeHostGeometry` 记在当前是否 Home 宿主，`-syncGeometry` 需要它。

**取舍说明。** dock 条带内不再铺视频，那里回到 **1.30 的显示效果**（系统背景）；桌面其余区域照常显示视频。这是刻意分开的：一个尺寸约束同时满足"桌面要有视频"和"dock 要正常"，而不是二选一。

## 1.32：桌面视频 CPU 降到正常水位（每帧探测改成按需探测）＋ 退出 App / 收起控制中心仍是 0 延迟 ＋ 素材预览图不再卡「生成中…」＋ 悬浮 dock 长按菜单接到背景视频

你报的三点，逐个说清楚**根因**和**改法**。

**① 开启桌面视频背景，SpringBoard / backboardd CPU 高。**
根因不在视频解码，在一段**每帧都跑的重型探测**。桌面视频一挂上，`coverWatch`（一个 CADisplayLink）就常驻，它每一帧都要：枚举所有窗口 → 逐个做类名匹配 → 进去遍历子视图 → 读 `presentationLayer` 做坐标换算，最后才判断「桌面有没有被盖住」。稳态下（视频正常播、桌面可见）这个判断**每帧都得出同一个答案**，但探测本身一秒要跑 60 次；ProMotion 设备上因为没设 `preferredFramesPerSecond`，实际是 **120 次/秒**。这就是「光是开着桌面视频就费电」的来源。

改动：
- **每帧探测加了一道极便宜的闸门**：先只数「当前可见窗口数」（每个窗口一次属性读，没有类名查找、没有 layer 查询、没有坐标换算）。所有会让覆盖状态翻转的事件都会改变这个数——App 窗口出现/消失、控制中心窗口取消隐藏/隐藏、切换器外壳来了又走。**数没变且距上次全量探测不到 1 秒，就直接返回**，不做重型探测。
- **闸门只管「正在播放」这个状态**。被遮挡（frozen）时**仍然每帧全量探测**——这正是保住 0 延迟的关键，见 ②。
- `preferredFramesPerSecond = 60`，把 ProMotion 上的 120 Hz 砍掉一半。
- 控制器树发现扫描从 1 秒一次改成 2 秒一次（它是发现型任务，不是每帧信号）。
- 音频同步定时器从 **10 Hz 降到 4 Hz**，音量写入改成先比值再写，音画漂移检查从「每一拍都读 `currentTime`」改成 2 秒一次。这三处每次都会跨进程访问媒体服务。

**② 退出 App / 收起控制中心的视频和声音 0 延迟。**
这条**没有被削弱**，是刻意设计的。闸门是**不对称**的：
- **恢复检测绝对不降频**。被遮挡时视频是暂停的（不解码），成本本来就只有探测本身，所以这个状态**保持每帧全量探测**，恢复落在同一帧。
- 只有「正在播放」状态才走闸门，而它需要发现的是「有东西盖上来了」——这时用户视线已经被盖住，最多 0.2 秒的发现延迟肉眼不可见，且 1 秒的强制全量兜住了所有边缘情况。
- 音频那两处直连 **没有动**：`coveredNow` 翻转瞬间的 pause/resume 钩子仍然是即时触发，不经过任何定时器。

**③ 素材预览图全部卡在「生成中…」。**
根因是两个叠加的缺陷：
- 取首帧用的是**同步** `copyCGImageAtTime:`，**没有任何超时**。遇到还在写入的文件、异常编码或损坏容器，它会把工作线程**无限期**堵住。而这张行的 key 会一直留在共享 `pending` 集合里——之后每次请求都变成 `skip-pending`，失败账本永远不增长，**连重试预算都花不出去**。表现就是永久「生成中」。
- `revision` 里包含了 `ctime`（inode 变更时间）。改权限、链接数变化、恢复流程都会让它动，于是**刚写好的海报在下一次查表时被判成 stale**，行重新解码、又把自己的新图丢掉，回到「生成中」。

改动：
- 取帧改成**可取消的异步形式 + 4 秒超时**（超时即 `cancelAllCGImageGeneration`），线程不再可能被堵死。
- 加**看门狗**：入队 20 秒后若 key 仍在 `pending` 且没有海报，强制清掉并记一次失败，让既有的重试路径用新线程重新排队。行再也不会被卡死。
- `revision` **去掉 ctime**，只保留 inode + size + mtime——这才是「文件内容是否变了」的诚实标识（替换文件会换 inode，重写会动 mtime），而元数据被动过不再作废一张好海报。
- 候选取帧时间从 `0 / 0.1 秒` 改成 `0 / 0.5 / 1.0 秒`。原来的 0.1 秒离片头太近，那些开头是黑场或淡入的素材会**成功取到一张全黑图**，然后被写进磁盘当预览图长期使用。

**④ 1.31 挂载太高导致图标一闪一闪。**
`atIndex:` 的目标算错了：设备上图标容器本身就在 index 0，所以「图标容器自己的索引」算出来也是 0，于是每一轮 reparent 都把图标容器往上顶一格，图标和视频互相换层——这就是闪烁，也解释了为什么视频卡在图标和 dock 之间。现在统一落到 Home 视图的**最底槽位**：这个位置**不需要任何原有兄弟节点让位**，闪烁从根上消失，视频依然合成在壁纸之上、图标之下。同一个 bug 的第二个出口（借用父视图那条路）也一并改了。

## 0.0.128：偶发闪壁纸的最后缺口——隐藏期逐帧监视，恢复延迟从 ~400ms 降到 ~16ms

## 0.0.126：打开/退出 App 不再闪原壁纸（遮挡判定跟随 App 的动画帧）

## 0.0.125：预览图设置/悬浮窗真正共享 ＋ App 覆盖桌面时 CPU 真正降下来

## 0.0.99：系统在视频之上又画了一遍原壁纸 → 临时抑制那两个「重画壁纸」的层

设备日志显示 `gapTop` / `sampledGapTop` 在所有样本里都是 `0.0`，`above` 里也只剩时钟
与通知列表这类非背景视图——即**几何与 z 序都已就位**。把 `SBCoverSheetWindow` 的完整
层级展开后，找到了压在我们之上的两个「重画原壁纸」的层：

```
CSCoverSheetView
 └ SBFTouchPassThroughView（可滑动内容）
    ├ SBDashBoardWallpaperEffectView   ← 面板背景（我们已在其上）
    ├ UIVisualEffectView
    ├ ▼ LMVLockVideoHost（0.0.98 起的落点）
    ├ UIView → SBFLockScreenDateView    ← 时钟
    ├ SBFTouchPassThroughView
    │   └ PBUIPosterFloatingLayerReplica → _UIPortalView   ← ① 壁纸浮动层实时门户
    └ CSScrollView
        └ CSMainPageView → CSCoverSheetViewBase
            ├ NCMaterialDisplayingCaptureOnlyViewControllerView  ← ② 通知中心「捕获壁纸」底板
            └ 通知列表
```

两者都在视频**之上**：① 是壁纸浮动层的实时门户，② 是通知中心捕获的壁纸底板。
从下方无法盖住它们，因此本版改为**临时抑制（lease）**：视频在屏时把它们 `hidden=YES`，
撤下时**原样恢复**（不摘除、不改结构，系统始终持有这些视图）。

抑制范围有严格限定，避免误伤：

- 命中类名：`NCMaterialDisplayingCaptureOnly`、`PBUIPosterFloatingLayerReplica`、
  `PBUIPosterFloatingView`、`PBUISnapshotReplica`、`SBDashBoardWallpaper*`、
  `*WallpaperEffectView`、`PBUIWallpaperView`；
- 尺寸必须覆盖面板（宽 ≥ 容器一半、高 ≥ 三成），所以通知卡片自身的磨砂底板不受影响；
- 只扫描**视频之上**的兄弟子树（下方的系统壁纸分支保持不动，关掉视频即恢复原样）。

日志新增 `leasedPaint=[...]`，直接列出本次抑制了哪些类。**若某次下拉仍露壁纸，
`leasedPaint` 为空就说明另有其层，`above=[...]` 会同时给出它的类名。**

## 0.0.98：下拉露出的原壁纸来自面板自己画的背景；切换 App 时画面不再闪掉

### 顶部/面板区域露出原壁纸

设备日志给出了决定性事实：`gapTop` 与 `sampledGapTop` 在 **209/209** 个样本里都是 `0.0`
——几何上视频一直盖住该区域。所以露出的是**绘制顺序**问题：

```
CSCoverSheetView
 ├ SBUIBackgroundView          ← 宿主原本插在它上面
 ├ SBFStatusBarLegibilityView
 ├ LMVLockVideoHost            ← 0.0.97 及以前在这里
 └ SBFTouchPassThroughView     ← 可滑动内容（sublayers=6）
    ├ SBDashBoardWallpaperEffectView   ← 面板自己再画一遍壁纸
    ├ UIVisualEffectView
    ├ ▼ ▼ ▼ 视频应该在这里
    ├ UIView / SBFTouchPassThroughView
    ├ CSScrollView              ← 时钟与通知列表
    └ CSFixedFooterView
```

可滑动内容自己画了面板背景（`SBDashBoardWallpaperEffectView` / `UIVisualEffectView`），
而它在 z 序上位于 `controller.view` **之上**，挂在 `controller.view` 里的表面永远盖不住它
——这就是下拉时看到的原壁纸。

本版改为：**当可滑动内容以一段"背景绘制"子视图开头时，把宿主放进该内容内部、就在这段
之后**（壁纸绘制之上、时钟与通知列表之下）。没有这种结构时，仍沿用原来的
`controller.view` 摆放，逐字节不变。

### 切换 App 时视频背景闪掉再恢复

`updatePresentation` 原来有一条 `(!ready && !posterLayer.contents)` —— 播放器一旦
`readyForDisplay` 瞬时变假（**冻结后恢复播放、解码器重新预热**正是这种时刻），就把
`renderLayer` 隐藏，于是露出系统壁纸，等就绪再恢复。

本版新增 `everReady`：**只要这一层已经显示过画面，就永远保留最后一帧**，`!ready` 只对
"从未显示过任何东西"的表面生效。

### 诊断

- `lock-video cover` 新增 `hostSuper=`（宿主落在哪个父视图）与 `above=[...]`（**宿主之上
  还在绘制的可见兄弟**列表）；`container=` 与它们一起构成完整的层级证据。
- `desktop-video` 新增 `hostHidden=` / `poster=` / `shown=`，用于区分"视频是被我们自己
  藏了"还是"被别的东西盖住"。

## 0.0.97：下拉不再漏壁纸；打开/退出 App 不再卡顿

### 顶部漏原壁纸（下拉通知中心）

面板由系统按屏幕刷新率驱动，而本插件的几何是**按显示链采样**的（0.0.96 起 60fps），
所以可滑动内容的"露出版面"边缘最多会比面板**慢一帧**——这一条窄带就是下拉时看到的
原壁纸。

本版给**正在移动的那条边加一帧前瞻**：用上一次采样到现在的位移，把该边沿运动方向
再推出一帧（上限 60pt）。只在版面**变大**时生效；版面变小时不加，所以面板收起仍然
照常撤下视频。日志相应新增 `lead`（本次前瞻量）与 `sampledGapTop` / `sampledGapBottom`
（**前瞻之前**本来会露出的量）：`sampledGapTop>0` 而 `gapTop=0` 即说明这一帧漏出已被
前瞻补掉。

### 桌面通道：打开/退出 App 时卡顿

退出 App 的过渡里，`_frontmostApplication` 可能有一帧读不到 bundle id（返回 0＝未知），
而 Home 的几何也在 App 窗口动画期间抖动。旧代码只把**明确的 -1** 当作"应用在前台"，
于是那一帧直接走了拆除分支（还原租约 + 摘掉宿主），下一帧再重新挂上——看到的正是
"卡一下"。

本版改为：**只要不是确定性原因（息屏／锁屏／通知内容未知／功能关闭／解码错误），
瞬时不可见一律保住宿主并冻结**，并给出 0.6s 的宽限窗口，让过渡中的抖动不再触发
拆除—重建。日志新增 `held=`（已保持多久）与 `teardown=`（累计真正拆除次数）：
`teardown` 不再增长即说明卡顿源头已被消除。

`desktop-video` 一行补齐了全部决策输入，掉背景时可以直接看出是哪一项否掉的：

```
desktop-video visible=0 frozen=0 home=1 host=none path=1 layer=0 contentHidden=0
```

## 0.0.92：修复下拉通知中心过程中顶部露出壁纸

CoverSheet 的层级是：

```
SBCoverSheetWindow
 └ SBFTouchPassThroughView            (controller.view，满屏、不裁剪)
    ├ SBCoverSheetPanelBackgroundContainerView   ← 面板自己的背景/模糊
    └ SBCoverSheetPositionView
       └ SBFTouchPassThroughView   ← 滑动时整体偏移的就是这一层
          └ CSCoverSheetView      └ clipsToBounds=1 ← 视频原本挂在这里
```

视频原本挂在 `CSCoverSheetView` 内、裁剪范围也只算「可滑动内容的可见区」。
面板滑动时整条 `PositionView` 分支被偏移，**面板没盖到的那一段就露出系统壁纸**，
而挂在面板内部的图层无论怎么放大都盖不到面板之外（`clipsToBounds=1`）。

本版做两件事：

1. **提升宿主**：当所在容器没能覆盖窗口可见视口时，把视频层提升到第一个
   「不裁剪 + 覆盖整个可见视口」的祖先（即 `SBFTouchPassThroughView`），
   插在**面板分支之下、面板背景分支之上**，层级关系不变。
2. **扩展裁剪**：提升后裁剪基准改为「窗口可见视口 ∩ 新容器」，视频铺满整屏。

**可见性判定不变**：仍然由可滑动内容的可见区决定，面板收起（内容滑出屏幕）时
`contentClip` 为空 → 视频照旧撤下，不会在解锁后残留。

## 0.0.84：修复控制中心 / 通知中心「降半屏」时视频背景消失

降半屏（面板不再全屏）时 `SBControlCenterWindow` / `SBCoverSheetWindow` 会被系统置为
`hidden=1`，而窗口仍占据整屏。旧代码把这个 `hidden` 当作「不该显示视频」的否决条件：

- `LMVLockVideoRectInTree()`：`window.hidden` + 祖先 `hidden` 遍历 → 几何直接归零
- `LMVCCVisibleViewport()`：祖先 `hidden` 短路 → 同样归零
- `update()`：控制中心通道复用桌面的 `LMVDesktopGeometryVisible()`，同样被 `hidden` 拦下

几何归零后 `LMVCCMaterial()` 首行即 bail、视频层被 `removeFromSuperlayer` 摘除，背景随之消失。
现在改为：**窗口/祖先的 `hidden` 不再作为几何否决条件**，只以 `LMVVideoWindowViewport()`
（窗口真正移出屏幕时返回零）作为几何基准；同时 `LMVCCMaterial()` 的高度判据改为
`MIN(viewport.height, material.height)`，使半高 material 在视口仍为全屏时也能命中。

实测证据（`/var/mobile/Documents/LMVDiagnostic.log`）：控制中心 `SBControlCenterWindow.hidden=1`
出现 16/40 次、通知中心 `SBCoverSheetWindow.hidden=1` 出现 30/40 次，均伴随 `viewport=(invalid)`；
703 次全屏样本、49 次塌零、真正的半屏几何一次都没采到 —— 全被 `hidden` 短路吃掉了。
